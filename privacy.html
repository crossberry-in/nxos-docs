NoxOS Privacy Principles

NoxOS is a privacy-first OS. These principles are engineering constraints, not marketing: every one of them maps to code, tests or a tracked gate in docs/SECURITY.md / docs/ROADMAP.md.

1. Data minimisation by construction

  • The kernel collects no telemetry. There is no analytics module, no crash-upload path, and none is planned in the kernel or system services.
  • Logs exist for the operator (serial console), not for network transfer. Nothing reads them back for reporting.

2. The serial log is a sensitive artifact

  • Fault dumps release-build redacted: exception class + fault status only; full register/address dumps are dev-build only (exception.rs::dump, audit v0.3.1 #16).
  • Kernel log lines are kernel-originated: userspace cannot inject log text (PUTCHAR is capability-gated, audit #13).
  • Future gate: per-subsystem log levels shipped default-conservative.

3. Capability-based permission model

  • Every syscall that touches a sensitive surface requires an explicit capability bit (security::CapabilitySet). Default = NONE.
  • Children/spawned apps inherit least privilege (currently DISPLAY only) until a full inheritance policy lands.
  • Planned: user-visible permission prompts per capability (roadmap P4), with revocation at the PermissionManager service.

4. Memory isolation roadmap (hard gates)

  • EL0 userspace will not ship until: TTBR1/kernel-VA reservation, per-ASID TLB invalidation, per-CPU caller identity and a returnable lower-EL exception path exist (see SECURITY.md §3.2 "Deferred" — these are gates, not suggestions).
  • W^X is enforced at boot today; user+X and W+X are rejected by the VMM.

5. Identity & networking honesty

  • No unique install/build identifiers are emitted by the kernel.
  • Networking begins in QEMU with virtual devices; no Wi-Fi/Bluetooth/ cellular compatibility is claimed until the chipset + firmware integration is actually tested (master spec §11). Location/wireless managers will expose state only after that verification.

6. Package integrity (planned .nxpkg)

  • Packages carry metadata, dependency info, digital signatures and per-file hashes; install verifies integrity before activation and supports rollback (master spec §14).
  • Signing keys never live in git (see the keystore finding in SECURITY.md §3.3 — being remediated by the owner).

7. Closed source ≠ security by obscurity

  • The source stays private (proprietary product), but the security posture is public: this document, docs/SECURITY.md, and the audit trail describe exactly what is enforced and what is not. Honesty over claims — an unverified statement in these files is a bug.
