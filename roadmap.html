NoxOS Implementation Roadmap

Maps the master specification (§20 Development Execution) onto verifiable milestones. Rule of the house: nothing is "done" without a passing automated test, and no compatibility claim exists without the actual hardware/firmware in the loop.

P0 — Foundations (DONE, verified)

Kernel core through the first graphical milestone, plus the v0.3.1 red-team audit and hardening pass. Evidence: docs/SECURITY.md §3.1, make smoke (dev + release) PASS, make qemu-graphics PASS, 120/120 host tests. Inventory: docs/STATUS.md.

P1 — Planning baseline (DONE this cycle)

  1. Repository inspection + inventory (docs/STATUS.md).
  2. Dependency map (diagram above; per-crate detail in docs/ARCHITECTURE.md).
  3. This roadmap.
  4. Security & privacy baselines (docs/SECURITY.md, docs/PRIVACY.md).

P2 — DeviceManager + IPC foundation (next)

  • DeviceManager kernel module: device registry, DTB-driven enumeration, driver binding, lifecycle + hotplug events, capability info, per-device permissions (spec §8).
  • MMIO device-region registry (closes SECURITY.md deferred item): accessors validate against registered regions.
  • Driver framework: trait-based driver model with init/identify/capabilities/state/config/events/error/shutdown/suspend/ resume contracts (spec §7) — the HAL traits sit on top of this.
  • IPC v2: channel close/reap (closes deferred item), shared memory with capability handles, async messages, service registry with versioning, timeouts (spec §9).
  • Tests: device-discovery tests against QEMU's generated DTB; IPC round-trip + permission tests (spec §19).

P3 — HAL + networking + storage

  • HAL modules: display, input, storage first (QEMU-verifiable), then the rest as contracts (spec §7).
  • VirtIO-block + VFS skeleton; VirtIO-net + IPv4/TCP/UDP + DHCP/DNS starting from QEMU virtual networking (spec §10).
  • x86_64 bring-up track: UEFI boot, APIC, PCI enumeration (spec §15).
  • No physical Wi-Fi/Bluetooth/cellular claims until chipset+firmware integration is tested (spec §11).

P4 — EL0 userspace (HARD GATE) + system services

Gate order (nothing ships before all four): 1. TTBR1 kernel/user split or reserved kernel VA ranges, 2. per-ASID TLB invalidation + break-before-make remap path, 3. per-CPU caller identity (no global syscall context), 4. returnable lower-EL exception path (kill the faulting task, not the machine).

Then: Rust system services (spec §12) behind the IPC service registry, each with versioned interface + tests.

P5 — Mozhi integration (closed source)

  • Mozhi freestanding mode targeting NoxOS syscalls/IPC (spec §5) — only after compiler + runtime + memory model + ABI are verified upstream.
  • NoxOS native launcher that installs the Mozhi .pkg/.nxpkg app format and opens apps in full windows (the lifecycle already proven in the Mozhi app platform: build → install → launcher → full window).

P6 — Native UI + application ecosystem

Window manager, launcher, control center, settings, file manager, terminal, notifications (spec §13) on the existing design-token system; .nxpkg package manager with signatures/rollback (spec §14); app SDK + Mozhi bindings.

P7 — Multi-platform verification

QEMU arm64 + x86_64 matrices, ARM64 dev boards, and only then device compatibility profiles for Android hardware (spec §15), each behind a verified profile document. Release pipeline per spec §17 (private artifacts, signed manifests, license audit).

Standing rules (from the master spec)

  • No Java/Kotlin/Gradle anywhere in the OS implementation.
  • No unverified placeholder code presented as features.
  • No deletion of existing functionality.
  • No completion reports without actual successful tests.
  • Public repos carry documentation only; source stays private.
